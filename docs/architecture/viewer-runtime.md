# 沉浸展厅运行时与原图渐进展示

核验日期：2026-10-24。状态：运行时设计；P0.5核心原型已实现，实际验证范围见[P0.5验收报告](../research/p05-validation.md)。本文的生产媒体 API、HDR及全部展厅仍是后续契约，不能将原型结果扩展为全部完成。旧HTML概念仅作为配色、排版和信息层级参考。

## 1. 新的产品约束

- A–F 六种展厅的主体画面统一由 **一个持久的 Three.js / WebGL canvas** 绘制，铺满可用画面；切换展厅复用 renderer、资源调度器和输入系统。
- 点击缩略图后立即展示可用的 4K 预览，再从 NAS 原路径后台读取该照片的原始成片，用数码暗房冲印动画完成清晰度过渡。这里的“原图”不包含此前排除的 RAW 或原片目录。
- 照片的真实颜色、方向、构图优先于舞台效果；动画结束后不能残留调色、颗粒、锐化或遮罩。
- 登录、刮削管理、配置仍可使用 React DOM。展厅不能用 DOM 相册、CSS 3D 卡片或六个独立 canvas 替代。必要的无障碍语义和输入辅助层与 canvas 共用动作状态。
- 首版维持准确 SDR 的验收顺序。单 canvas 下原生 HDR 的可行性需要单独验证，不能直接假设浏览器能够把原生媒体的 HDR 完整保留到 WebGL 纹理和最终显示。

上述是用户确认方向；以下接口、预算档位和性能门槛是实现提案，需通过 P0.5 原型收敛。

## 2. 一套运行时，六种空间组织

React 负责服务状态、登录与页面生命周期；`ExhibitionRuntime` 持有唯一 renderer、主 canvas、输入路由、相机、场景切换和帧循环。`SceneMode` 只提供布局、可见范围、拾取目标和转场参数，不自行创建渲染器或网络队列。

建议共享以下模块：

- `ExhibitionStore`：当前活动、当前资产、筛选、时间锚点、缩放位置、查看原图状态；模式切换不丢失当前位置。
- `SceneMode`：进入、更新、离开、保存锚点；退出释放该场景独占几何和材质，共享纹理交还资源池。
- `MediaScheduler`：可见缩略图、当前 4K、当前原图、相邻预览分别排优先级，并统一处理取消、去重和预算。
- `TexturePool`：纹理拥有者、引用计数、估算字节数、上传状态和淘汰；不由某一张照片组件隐式拥有全部生命周期。
- `InputRouter`：鼠标、触摸、键盘、缩放和拾取；纵横手势先判方向，防止同时翻活动和翻照片。
- `CanvasHUD`：时间线、标注、图标、进度和可见按钮在同一 canvas 内渲染；对应的键盘焦点、标签与状态提示有轻量 DOM 语义映射。

六种模式均由这套运行时实现：

- **A 时空隧道**：透视相机、照片平面和深度层次；每个活动的代表照片作为一组场景对象。只保留当前及邻近活动的纹理，远处以低级别预览表达。
- **B 双轴主题展览**：纵轴是活动，横轴是活动内照片；使用虚拟坐标和相机移动，非页面长列表。作为首版完整体验，先解决进入活动、看图、返回位置和快捷导航。
- **C 日历**：正交相机与可拾取网格，在年、月、周间改变布局与内容密度。只有确定到日的时间能进入日格；年份/月份级日期仍保留其精度。
- **D 地理展厅**：地理投影、地图瓦片、活动聚合与照片都在主 canvas 中绘制。初版可先适配栅格 XYZ 瓦片到平面，再评估矢量数据到几何/文字的适配；不嵌入会创建第二个 map canvas 的地图组件。来源署名、缓存许可、离线许可和瓦片服务限额需在选 provider 时逐项确认；地图截图或瓦片缓存不能默认有再分发权。可见署名绘于 HUD，同时提供可访问的来源链接。
- **E 设备展厅**：设备线条图标转为矢量路径/几何或有界图集，与照片平面共同渲染；用设备事实筛选，不把推断设备误当成实测 EXIF。
- **F 满屏照片墙与屏保**：实例化照片平面填满视口，可按随机、时间和筛选渐进更新。网格可裁切成接近正方形，打开单图时恢复完整构图。后续的缓慢漂移、胶片带和单张巡展继续复用同一场景、调度与计时器。

模式支持共用资源不表示首版同时完成六个展厅。P0.5 证明空间切换和调度结构；P1/P2 先完成 B 与单图查看，其余逐步接入。

当前 Three.js 的 `WebGLRenderer` 使用 WebGL2；WebGL1 已不在其支持范围内。正式实现时锁定并记录实际 Three.js 版本及浏览器基线，不能把“存在 canvas”当作设备满足能力要求。[Three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)

## 3. 全屏与沉浸输入

进入展厅后 canvas 始终占满浏览器可用视口，响应尺寸、屏幕旋转、安全区域和设备像素比；渲染分辨率可以根据预算低于物理像素，但布局始终满屏。暖白画廊与暗色单图由场景状态切换，避免把网页卡片、侧栏和滚动条带入展厅。

“进入展厅”这一明确操作中申请系统全屏。Fullscreen API 要求用户激活，异步请求也可能被拒绝；不能在后台加载完成时自动补一次请求。监听进入、退出和失败，失败时维持同一 canvas 的视口满屏体验，状态中准确区分“视口铺满”和“系统全屏”。保留退出按钮和浏览器正常退出方式，不申请键盘锁来阻止退出。[MDN requestFullscreen](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen)

无障碍语义层提供当前活动/照片名称、前后切换、退出、播放/暂停、加载状态和焦点顺序。可见舞台与语义层使用同一个动作 ID 与状态，避免两套选择结果。读屏、键盘、减少动态效果是运行时要求，不等到六个展厅完成后再补。

## 4. 缩略图 → 4K → 原图的状态机

网络请求、解码/上传和用户视图是三种不同状态，不能用一个 `loaded` 布尔值概括。

1. **`thumbnail_visible`**：用户点击时保留已显示纹理，在相同构图/方向上进入单图场景，不出现空白背景。
2. **`preview_loading` → `preview_ready`**：优先取得本地 4K 缓存，完成解码、颜色处理、纹理上传与首帧绘制后替换缩略图。4K 请求失败则保留缩略图并允许重试。
3. **`source_loading`**：默认在 4K 首帧就绪后，后台读取同一资产版本的 NAS 原始成片。轻量元数据清单与缓存状态可与 4K 并行读取，原图大流量不抢占当前 4K 的快路径。若高质量缓存已就绪，可以直接使用；迟到的 4K 不能将已可见的高质量画面降级。
4. **`source_received` → `detail_preparing`**：下载完成后仍可能需要格式转换、解码、分块与 GPU 上传。此时可明确显示“已读取，准备细节”，不能宣布原图已可见。
5. **`detail_ready` → `developing` → `detail_visible`**：只有当前视口所需的高分辨率纹理已就绪，才触发冲印揭示。缩放到新区域时继续按块补充；未就绪区域始终有 4K 底图。
6. **`detail_unavailable` / `source_changed`**：原图不可访问、转换失败或源版本变化时保留 4K，提供准确状态和重试。源访问失败不等于照片被删除。

大图分块时，`detail_visible` 表示当前视口具备原图级细节，不表示完整原图的所有像素都已常驻显存。内部同时记录 `sourceTransferState`、`visibleDetailState` 和 `qualityLevel`，界面文案据此生成。

### 暗房冲印的表现

- 等待期间 4K 图保持清晰可用，只有轻微的边缘光感或纸面呼吸提示；不能为制造“显影”而把已清晰的预览故意模糊到难以观看。
- 原图细节就绪后，通过轻微颗粒消退与局部清晰度揭示完成短转场。暂以 300–700 ms 作为原型范围，实际时长由概念与交互验收决定。
- 动画只遮蔽资源切换，不伪造下载进度；有可靠总字节数才显示百分比。不能依靠固定倒计时宣称加载完成，也不能延迟已就绪原图来凑固定等待时长。
- 等待中仍能缩放、切图、退出；打开减少动态效果时改为直接替换或短交叉淡入。原图失败时停止等待效果，保留可交互预览。
- 新旧纹理使用一致的 EXIF 方向、裁剪、相机锚点和色彩转换；禁止在切换时旋转、跳位或改变曝光。动画结束后回到不加艺术处理的照片材质。

## 5. 媒体 API、来源版本和取消

API 接口名在 P1 可调整，但以下语义应提前固定：

- `GET /api/assets/{asset_id}/render-manifest`：返回稳定资产 ID、内容版本、尺寸/方向、源格式与颜色信息、4K/缩略图版本、Live Photo 配对、当前可用展示方式以及高分辨率准备状态。
- `GET /api/media/{asset_id}/{content_revision}/{variant}`：经馆主会话鉴权读取 thumbnail、preview4k 或已就绪细节资源。URL 使用不透明 ID，不暴露 NAS 用户名、密码、任意文件路径或完整源 URL。
- 高分辨率转换/瓦片需要 worker 时，使用可查询、可复用的准备任务，返回任务状态；已存在结果直接复用。传输重试与转换重试分开，避免一个慢请求反复生成相同产物。
- 对需要流式播放/拖动的视频、Live Photo 动态部分和大文件传输保留 Range/条件请求能力；后端应核验 NAS 的实际支持，正确处理 200/206/416、内容长度、ETag 和断流，不能伪造 NAS 不提供的续传能力。

浏览器只访问同源 webserver；源适配器在服务端把资产记录解析到 NAS 根目录内的已索引相对路径。严格规范化路径与编码，拒绝越界路径、任意 URL 和由浏览器直接传入 NAS 地址的代理请求。共享密码产生的会话授权同时覆盖清单、缩略图、原图、瓦片与动态媒体；注销或过期后不因“静态缓存文件”路径绕过权限。私密媒体不进入公共 CDN 或公开缓存。

`content_revision` 基于可用的源校验信息与服务端资产版本生成；先记录强/弱 ETag、大小、mtime 等证据，不能把缺失或弱 ETag 当成可靠内容哈希。下载前后发现源变化时作废这次产物，重新索引/生成对应版本；不会把旧 4K 与已变更原图无提示混合。需要强一致校验的文件可在读取过程中计算内容哈希，不为全库初始展示强制先读完所有原图。

每次单图选择生成一个 `view_generation`，每个请求带资产 ID 和内容版本。快速 A→B→A 时，即便旧请求晚到，也必须核对三者后才能绑定当前材质。`AbortController` 取消过时请求；已进入解码或上传的结果同样需要丢弃检查与释放，不能只依赖 HTTP 取消。资源池可合并相同资产版本的请求，但仅在还有使用者时保持高优先级；退出展厅后暂停预取，不能继续读取整批 NAS 原图。

原图读取优先于后台批量缓存时需要限额，避免抢占全部 worker 和 NAS 连接。建议原型从“当前原图 1 个、少量相邻 4K、可见缩略图优先”开始测量，再决定默认并发数。

### 原始文件与可显示细节不是同一概念

能够原生解码的格式也必须通过画面和颜色验收。无法在目标浏览器正确解码的 HEIC/HIF、带特殊色彩空间或 HDR 的文件，由服务端从原始成片生成高分辨率 SDR 兼容图/瓦片；这是由原图得到的细节展示，不应声称是“原文件原生 HDR”。需要时保留明确的原文件下载操作，和展厅显示状态分开。

原图可能已经小于 4K，也可能与缓存处于相同分辨率。此时仍可按需要读取原文件，但不做虚假的“更高清”承诺；状态依据实际像素尺寸、采样级别与转换方式生成。

## 6. 显存、解码内存和原图瓦片

磁盘 WebP 文件很小不代表纹理很小。按 RGBA8 估算，3840×2560 图像的基础纹理约 37.5 MiB，含完整 mip 链约 50 MiB；10 张同时常驻约 500 MiB。6100 万像素的基础纹理约 233 MiB，完整 mip 链约 310 MiB。它们还没有计算 CPU 解码副本、上传暂存、过渡期的新旧纹理和渲染目标。这些是预算算术，不是实测浏览器占用。

因此，活动的 10 张代表照片不等于同时上传 10 张 4K，更不能把约两万张照片加载进 GPU。正常展览按屏幕投影尺寸选择缩略图或 4K；只有正在查看的照片进入高分辨率链路。

启动时读取 `MAX_TEXTURE_SIZE` 等能力，根据分辨率、可用目标格式和运行表现确定档位；不能假定所有终端支持同一最大边长。WebGL 无通用的可靠可用显存查询，使用自己的字节账本和保守预算，并把 `renderer.info` 的计数作为辅助观测，不能把它报告为真实显存字节数。[MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)、[Three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)

高分辨率策略：

1. 能在边长和内存预算内安全上传的小原图，可作为单张新纹理替换。
2. 超过边长或预算的大原图，读取源文件后按需准备多级瓦片，按缩放级别、可见区域与邻近边界加载。保留 4K 底图补缺口，限制每帧上传量。
3. 不为整库预生成完整原图金字塔；按被查看的资产版本惰性生成，并在服务端统一缓存预算内淘汰。第一期可先以 JPEG/兼容 SDR 瓦片验证，格式选择由测量决定。
4. 先生成/提供当前视口需要的层级，缩放再请求更细层级。纹理池记录瓦片边界、重叠采样和级别，验证接缝与快速缩放时的闪烁。
5. 视口、EXIF 方向和像素坐标共用一套变换，4K 与高分辨率层的切换不能改变用户的放大中心。

P0.5 可先试 64/128/256 MiB 的照片纹理软预算档位，另留 backbuffer、深度缓冲、后处理和地图预算；这些档位尚未证明适用于目标手机。DPR、同时驻留照片数和特效开销随档位调整，不能为了达标把原图细节永久降回 4K。

离开场景或淘汰资源时，分别处理纹理、材质、几何、render target 与 CPU 解码资源的归属。移除场景对象不等于释放 GPU 资源；共享资源按引用计数释放，`ImageBitmap` 不再使用时需明确关闭。[Three.js 资源释放手册](https://threejs.org/manual/pages/how-to-dispose-of-objects.html)

原图替换不通过修改已使用纹理的尺寸/格式强行复用；新旧纹理过渡期间明确预留峰值，切换后再释放旧资源。[Three.js Texture](https://threejs.org/docs/pages/Texture.html)

## 7. 服务端缓存仍受一个总预算控制

现有 80 GB 默认上限继续作为待验证的统一总预算，而不是在它之外再无上限保留原图。缩略图、4K、视频兼容文件、Live Photo 动态文件、原图暂存、转换中间文件和高分辨率瓦片都要记账。

现有样本推算的静态照片缓存约 8.52 GB、保守估计约 35.16 GB，仍只支持此前的缩略图/4K 预算判断；新增原图暂存和瓦片会产生访问相关的空间与写放大，不能把旧估计当成新链路的总容量证明。

缓存管理器须提供写入前预留、并发任务峰值预算、失败临时文件回收、最少空闲盘空间门槛和有使用者的资源保护。预算不足时先淘汰可重建且无人使用的原图暂存/细节瓦片；不能删除 NAS 原文件，也不能为了兑现“原图必读”而突破硬上限。确实无法准备时保留 4K 并说明细节暂不可用。

浏览器也只保留有界内存和短期私密响应缓存，首版不增加永久整库 Service Worker 缓存。未来若增加离线模式，需单独设计设备占用与注销清理。

## 8. 色彩、HDR 与单 canvas 的边界

首版输出目标是可验收的 sRGB SDR。输入照片必须经过正确颜色解释/转换；不能仅把 Display P3、Adobe RGB 或 HDR 数据标记为 sRGB。标准 SDR 色彩纹理按 sRGB 标记，混合在正确线性空间完成，最终输出只进行一次显示转换。照片材质不叠加照明和默认艺术调色；自定义暗房 shader 结束后仍回到同一标准输出。[Three.js 色彩管理手册](https://threejs.org/manual/pages/color-management.html)

4K 缓存和原图兼容展示应使用同一方向与色彩策略，并记录转换器版本。以原图制作的 SDR 高分辨率瓦片也要与 4K 在色调上匹配，否则清晰度过渡会变成曝光跳变。不能用逐帧强行调色掩盖两条转换链的不一致。

Three.js 当前公开手册的典型流程围绕 sRGB / Linear-sRGB；这不能直接证明所有浏览器都支持期望的宽色域/HDR 单 canvas 输出。WebKit 的 Canvas HDR 工作也区分 Canvas2D、WebGL、WebGPU 等路径；某项实现合入或某个原生 `<img>/<video>` 显示正常，不代表本项目的完整纹理、shader、后处理和输出链已经正确。[Three.js 色彩管理手册](https://threejs.org/manual/pages/color-management.html)、[WebKit HDR Canvas 跟踪](https://bugs.webkit.org/show_bug.cgi?id=276502)

后续 HDR 验证需记录浏览器版本、操作系统、显示设备、源传递函数/色域、解码路径、纹理格式与最终输出。Display P3 与 HDR 是两个不同维度，分别验收。若 WebGL 路径不能满足目标，再比较 WebGPU 渲染路径或原生媒体桥。**原生媒体桥会改变“单 canvas 展厅”约束，目前没有获得作为例外的确认，不能预先把 DOM 原图覆盖层写入已定方案。** 在作出后续产品决策之前，准确 SDR 单 canvas 为正式基线。

Live Photo 和普通视频同样经过运行时调度。动态帧作为纹理进入主 canvas，未播放时显示静态图/中间帧；播放需单独控制解码开销、视频颜色和音频状态。不要把视频上传成功等同于 HLG 已被正确转换。

## 9. 故障恢复与交互连续性

- 页面后台、退出展厅时停止非必要动画、原图预取和视频播放；返回后先恢复当前可见层。
- WebGL context 丢失时保留 CPU 端选择/锚点状态，停止提交，恢复后从有限缓存重建可见纹理；不循环重扫 NAS 或重新请求整库。
- 尺寸/DPR 变化、设备旋转和进入/退出全屏时保留构图中心，重新选择瓦片级别。
- 原图离线、登录过期、缓存被淘汰和源内容版本变化分别显示准确状态；网络错误不会抹掉已可看的照片，也不会篡改索引中的删除状态。
- 暗房、场景飞行和屏保动画都遵循减少动态效果与暂停设置；静止查看时优先按需渲染，避免持续空转。

## 10. P0.5 风险原型与验收门槛

在正式画廊 UI 和生产缓存实现前插入 P0.5。只验证最小贯通链路，测试素材和网络夹具不得被误称为真实 NAS 验收。需要覆盖以下可复现检查：

1. **单 canvas 骨架**：B 的简化布局、F 的简化墙和单图查看共享唯一 canvas/renderer；切换不重建 context。模拟两万条元数据并虚拟化，只对可见及少量邻近照片申请纹理。
2. **三阶段加载**：冷/热缓存，4K 先就绪、高质量缓存先就绪、原图延迟、原图失败、解码失败、源文件变更；验证先有可看照片、画质不被迟到预览降级、动画不提前完成、错误仍能操作。
3. **取消竞态**：连续 A→B→A、切换模式、退出展厅、会话过期；记录请求、解码和资源计数，确认旧结果不覆盖新选择，取消后的临时/CPU/GPU 资源可回收。
4. **6100 万像素与边长边界**：使用可公开提交的合成尺寸/色块图测试；超过实机 `MAX_TEXTURE_SIZE` 时走瓦片，快速平移缩放无黑洞、接缝、跳位和无界内存增长。实际私密样本另放忽略目录验证。
5. **颜色与转场**：sRGB 测试图、真实 SDR JPEG、HEIC/HIF 兼容转换、已知 HDR→SDR 样本；静态前后逐项比较方向、裁剪、肤色、灰阶和高光，确认动画退出后没有残留处理。不能只看“文件成功生成”。
6. **原图来源与访问**：测试资产 ID 越权、路径越界、过期会话、旧版本 URL、Range 与断流；服务端保持 NAS 只读，浏览器看不到 NAS 凭证。
7. **全屏与可访问性**：用户点击进入、请求被拒、主动退出、键盘与触摸、手机旋转、减少动态效果和读屏标签；所有分支维持同一展厅状态。
8. **资源恢复与预算**：受控 context 丢失/恢复、后台/前台、连续浏览至少 100 张与反复进出场景，观察 CPU/GPU 账本和服务端临时盘。峰值在所选预算内，释放后的驻留量回到可解释范围。
9. **地理适配探针**：在同一 canvas 绘制少量可合法使用的地图瓦片、活动点与署名，证明不会暗中引入第二个地图 renderer；实际服务商选择和许可仍在后续完成。

建议初始性能目标为：记录明确设备/浏览器/分辨率下，桌面主要交互帧时间 P95 ≤16.7 ms、手机 ≤33.3 ms；当前 4K 已在服务器缓存且局域网正常时测量首帧延迟，并在证据里同时保留传输、解码与上传时间。以上是待测门槛，不是当前承诺的兼容范围或完成结果。

原型证据至少保存：版本锁、测试矩阵、每次传输和资源生命周期事件、设备/浏览器信息、关键截图/短录屏、失败用例与结论。只有实际跑通的验证流程再整理为项目 skill。通过后再锁定正式媒体 API、资源档位和展厅实现顺序；未通过的路径必须先调整计划。
