# CPU、静止渲染与过渡性能修订

2026-10-26。按馆主指定顺序：先后台 CPU，再静止渲染，最后过渡响应与帧调度。正式 8790 已发布；保留原数据、登录会话、队列与暂停设置，没有修改 NAS 或重刮全库。

## 结果与测量边界

CPU 使用累计进程时间差、按采样间隔加权；100% 表示一个逻辑核心，本机共 10 核。前后都没有新增完成事件或分析结果，不把实际推理负载算作空转。基线 71.556 秒，修订后 62.197 秒；属于同机运行采样，不是完全隔离实验。

- 服务合计 **300.32% → 12.86%**，减少 **95.7%**。
- API **127.86% → 8.98%**。
- 媒体、视觉、摄影、美学四个 worker 合计 **171.85% → 约 3.20%**。
- 本次没有测真实全量刮削吞吐，不承诺相同百分比的任务加速。任务执行、暂停恢复、租约及锁竞争由隔离回归验证。

旧分析 JSON 总计约 414 MB，绝大部分是特征向量。此前多个 worker 空闲时重复查询、提取 JSON；API 的馆务/设置轮询也重复执行全库聚合。其他仍打开的页面会增加这些请求，不能只看当前可见 Gallery。

原始采样留在被忽略的 `data/runtime-health/`、`data/transition-perf/final-cpu/`。旧诊断见 [runtime-health-2026-10-26.md](runtime-health-2026-10-26.md)。

## 后台修复

迁移 014–016 增加事务内 catalog/work/telemetry 变化计数及覆盖索引；热查询只读取所需版本、分数、错误和首个标签，避免解析整份 embedding JSON。无变化 UPDATE、访问时间刷新和 worker 心跳不触发重型工作。

空闲 worker 每秒检查廉价变化计数，新工作/设置变更能唤醒；无变化时最多 30 秒做一次完整检查，以覆盖时间到期的重试、租约和磁盘状态变化。媒体心跳仍每 5 秒维护。完成工作后继续执行，不以延迟每张照片换取低 CPU。

Gallery 使用单次构建、按版本失效的目录快照；馆务/目录/设置使用每端点最多 8 项的进程内快照。进度变更立即使快照失效，活跃工作还限制为最多 1 秒，其他读取最多 30 秒。每次 HTTP 请求依然先鉴权，快照不绕过权限。Gallery 的健康轮询改用轻量 `/api/session`；隐藏文档暂停轮询，未变化目录不反复触发 React 渲染。

## GPU 与静止页面

去掉封面的永久 `will-change`，仅运动期间启用；隐藏场景暂停 CSS 动画。过渡中避免同时变换大量 4K/原图纹理，暂时关闭照片档案等大区域的背景模糊；移除飞散克隆的动态 blur，限制最多 24 张克隆。

独立 Chrome、1600×900 合成图库的 5 秒静止 trace，修改前后均为 **0 Paint、0 DrawFrame、0 运行中动画**。这证明该空闲场景没有持续重绘，**不能证明修订降低了单页 GPU 百分比**。全设备 GPU 采样旧均值 53.87%、新均值 57.87%，还包含其他浏览器和 WindowServer，不具有单页前后归因意义。当前不能把 GPU 优化标成量化验收完成。

## 图片与过渡

队列里的 img 尚无 src 时，浏览器会画原生破图图标；这并不等于 HTTP 失败。共享 PreviewImage 在绘制就绪前隐藏图片表面、保留占位几何，真实错误仍走状态组件。隔离慢请求验证从 14 个可见未就绪图面降为 0；最终正式照片流截图的 17 个可见图面均成功加载。

预热同时覆盖前 15 项缩略图，点击时提升到前景优先级；照片流先显示缩略图，入场结束后再启动 4K 升级。单图复用共享缓存，避免重新请求同一 4K。每个已挂载虚拟格子保留一个小缩略图，4K 完成后隐藏，在返回动画时复用；虚拟格子卸载释放两者，不保留原图队列。缩略图仅是运动表面，静止仍展示 4K。原图就绪后的显影保留，离场暂停而非重启显影。

同一隔离服务、同一 1600×900 合成集合，分别加载保存的基线构建与最终构建，每条路径 3 次，中位数为：

- Cover Flow → 照片流：点击到结束 **1178 → 729 ms**，缩短 **38.2%**；新场景出现 **328 → 195 ms**。
- 照片流 → 单图：**995 → 563 ms**，缩短 **43.4%**。
- 单图 → 照片流：**1096 → 712 ms**，缩短 **35.1%**。
- 照片流 → Cover Flow：**995 → 695 ms**，缩短 **30.1%**。

最终点击到首段动画中位数约 12 ms；两版合成场景的 rAF p95 都约 16.7–16.8 ms，不能把缩短动画时长写成 FPS 提升。最终 12 次过渡没有超过 33.4 ms 的帧间隔，无浏览器异常或 HTTP 错误。

## 真实图库复核与剩余问题

在用户已解锁的 IAB 使用应用显式诊断模式 `?diagnostics=transitions`，记录 rAF 与 Long Animation Frame；不读凭据，不读取浏览器内部进程接口。诊断仅在该参数下运行，只在页面隐藏 output 中保存最近 12 次、不联网导出；退出模式不创建观察器。

最终一次真实封面→墙、墙→封面分别约 **757 / 765 ms**，p95 **17.0 / 16.9 ms**，无超过 33.4 ms 的帧间隔。墙→单图、单图→墙分别 **561 / 882 ms**，p95 **17.1 / 17.0 ms**，仍各有一次 **117 / 133 ms** 长间隔。分阶段状态提交仅数毫秒，长动画帧的 scripts 为空，停顿落在渲染区间；这不能进一步区分 GPU、纹理上传、宿主合成或其他系统竞争。此前同机返回样本曾达到 267–384 ms，短样本不是稳定分位数保证。

因此：CPU 空转已显著改善、破图等待状态已修复、动画响应及总时长改善；**真实高分辨率单图返回偶发长帧仍未完全消除**。后续应围绕高分辨率表面的首次合成/恢复继续测，不能宣称全路径稳定 60 fps。当前已关闭诊断模式，页面停在正式 Gallery。
