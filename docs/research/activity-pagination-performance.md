# 活动照片流分页瓶颈

2026-10-26。起因是馆主反馈一个265项活动的读取提示反复出现且等待较久。真实路径、照片清单和采样保存在被忽略的data/cat-loading，公开记录仅保留汇总。

## 实测原因

活动接口原先每页调用全库rows()：读取约18,963条展示记录、全库美学评分和Live Photo配对，随后在Python中按活动ID筛选。即使只要15张，也承担整库查询成本。照片流初次预热15项、随后200项、最后50项，每页重复该过程。

同一正式库只读端点函数测试（含cProfile，不含网络和浏览器解码）：三页原耗时5.394、4.152、6.133秒；优化后0.135、0.129、0.120秒。三页平均从5.226降至0.128秒，约缩短97.6%。这不是完整页面加载时间，也不是跨设备稳定基准。

本地文件读取另抽样15张：thumb合计约0.59MB、平均1.68ms；display合计约12.1MB、平均1.86ms。仅测现有缓存的文件读取，不包含HTTP排队、图像解码，不能以此承诺所有4K都瞬间显示。但本次秒级主要瓶颈明确在元数据全库查询。

## 修改

- 活动ID仍为既有哈希，不暴露源路径。先从轻量目录键解析范围，再用source_id/parent索引约束重型JOIN。根目录直属文件、跨源同名主题和年度主题沿用原分组方式；不新增跨请求结果缓存。
- 美学分可按活动内ID分批读取（每批最多800），保留原版本/媒体时间戳有效性条件。其他全库调用保持原行为。
- Live Photo配对查询同样限定活动范围；排列、分页大小、照片数和字段保持不变。
- 照片流已有内容足够当前视口时，补页在后台进行；滚到待补页边缘才显示中央加载状态。实际错误仍展示，不把失败隐藏成成功。
- 动画执行与数据读取状态分开，纯返回/入场动画不再标成“加载照片”。照片流及单图期间暂停15秒全库封面轮询，回到展厅后继续。

## 验证与边界

同一SQLite只读快照运行旧/新端点，对三个分页响应逐项比较，265项、顺序、统计和字段完全一致。只读性能测试不GET NAS、不重新生成缓存、不运行识别或修改正式照片。

8项活动范围/媒体/美学测试及12项封面/时间线/展厅/HTTP缓存回归通过（20项）。新增根目录独立分组、活动隔离、分页一致与按活动读取评分检查。隔离265项合成分页的5组浏览器检查覆盖后台预取不弹窗、15秒不重查封面、边缘真实等待、完成后消失、返回动画不冒充读取，零浏览器脚本异常。
