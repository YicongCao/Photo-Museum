# 策展检索工具：嵌套参数、空地址与地名层级

2026-10-25。一次真实运行在多轮探查后达到8轮上限，未创建展览。本轮读取持久工具事件并在本机只读重放，未重发原私人策展请求；完整运行记录、查询结果及真实库收据仅保留在忽略的 `data/curator-search-fix/`。

## 已确认原因

1. 兼容Provider实际返回的参数形如 `{"filters":"{\"city\":[\"某城市\"]}","limit":5}`。`filters`是再次编码的字符串，原Pydantic模型只接受对象，带条件检索在进入搜索前就失败。无条件检索成功，因此不能把该错误解释为城市或主体不在SQLite中。
2. 将参数改为对象后，真实库还触发了第二个缺陷：部分有效地点有 `province:null` 等空字段，原始值直接进入 `.casefold()` 或字符串拼接，导致省份/关键词搜索抛出AttributeError或TypeError。已有分类统计过滤过空值，解释了“facets能列出、search却失败”的现象。
3. 原运行把校验、句柄和部分内部执行异常都归为同一个笼统提示，模型无法区别参数错误与正常0结果，反复更换条件直至耗尽轮次。
4. 地点精度是另一个独立边界：现有GeoNames provider返回最近城市/镇，不保存地级市行政归属。中文地级市名及其英文拼写都为0时，不能仅凭附近镇名或活动标题补造该市拍摄结论。

## 修复

- 仅对声明为对象的 `filters` 字段兼容一次JSON解码，随后仍执行完整白名单、类型、范围及长度校验。无效JSON、数组、null、标量、未知键仍拒绝，不能失败后退回空条件。
- 发给Provider的嵌套工具schema展开本地 `$ref`，明确对象结构；提示词加入实际调用例子、错误修正方法和地点精度边界。
- 地点可检索值只包含真实非空字符串；未知显示标签不会成为拍摄地点事实。facets与搜索都匹配中文显示名和原始拼写，计数不因双语重复。
- 工具错误保留字段路径/错误类型/修正提示，不回传被拒绝的值和堆栈。参数校验、业务请求和内部工具失败使用不同错误码；内部失败停止运行，连续3次无效调用也停止重复尝试。
- 原失败任务及事件不修改，不自动重新发送付费请求。

## 验证

完整后台回归 **132项通过**；新增 `tests/p1/test_curator_search.py` 覆盖双重编码的真实调用形状、畸形参数不放宽、空地址、多语言facets、地级市不借标题命中、错误隐私、SSE→工具→准备展览整链路，以及连续参数错误/内部错误止损。

真实库仅用只读SQLite并调用本地检索函数：省份、主体、关键词和字符串filters重放均已成功；没有读取NAS原图或重刮。标题匹配得到的是活动线索，未将它们作为已验证的城市结果。

真实hy4-preview验证只发送三张程序生成图片的文字索引：24.47秒内完成catalog_schema、library_overview、search_photos、create_exhibition，3/3缓存核验通过并创建合成展览；没有向Provider发送私人照片或真实地名检索结果。公开摘要见 [验证收据](curator-search-tool-evidence.json)。

地级市/区县行政层级补全未在本轮实现；仍须补充有来源的行政数据并保留精度，不能通过修改提示词把镇名猜成行政归属。机器主体标签仍为候选，不等于人工确认的照片主角。
