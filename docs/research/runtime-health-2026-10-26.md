# Runtime health — 2026-10-26

## Conclusion

服务仍能运行，但后台无产出时的 CPU 开销偏高，不能认定运行效率健康。优先优化工作队列查询，其次定位 API 重复查询。当前证据不足以给 Gallery 单页 CPU/GPU 下结论。

本次只读检查，没有重启、暂停刮削、修改配置或改动应用代码。

## Measurement

- 本机 10 个逻辑 CPU、24 GiB 内存。CPU 100% 表示一个逻辑核，不代表整机满载。
- 约 21:50–21:53（Asia/Shanghai）采集进程、驱动和调用栈。连续 CPU/GPU 窗口为 71.556 秒、30 个样本；CPU 根据累计进程 CPU 时间差计算，下面汇总均按实际间隔加权。
- 保留用户当时的浏览状态，没有进行受控的页面空闲/滑动 A/B 实验。诊断本身也有少量开销。
- 原始数据与栈采样仅存于被 Git 忽略的 `data/runtime-health/`，不提交私有运行记录。

- 服务进程合计平均 **300.32% CPU**，同时采样峰值 **353.77%**，约占整机逻辑核容量的 **30%**。

- 窗口前后完成事件计数相同；没有最近一分钟更新的单图处理阶段或分析记录。媒体队列各状态计数也没有变化。这些高 CPU 不能用本轮正在完成图片转换/模型推理来解释。
- 媒体 worker 的独立三秒栈采样中，主线程 249 个样本有 226 个落在 SQLite 执行路径，包含大量 JSON 提取和解析。API 的独立栈样本也出现多个繁忙 SQLite/JSON 执行线程。

代码核对：`photo_museum/work_queue.py` 的 `directory_focus()` 联接 entries/media_jobs/jobs/media_info，并对分析结果执行相关子查询与 `json_extract`；`choose_directory()` 被多个 worker 调用。**多 worker 重复检查昂贵的待处理投影是最值得先验证和优化的热点**。栈证据说明 SQLite/JSON 成本，尚不能把所有 API 成本精确归到某一个 HTTP 接口。

## Browser and GPU

- Codex 宿主中全部可识别 renderer 合计 CPU 平均 **16.76%**，同时峰值 **71.51%**。它包含宿主界面及其他渲染上下文，**不等于 Gallery 单页**。
- Codex GPU 进程的 **CPU** 平均 **9.31%**，峰值 **16.20%**。这是 CPU 执行成本，不能当 GPU 利用率。
- 驱动提供的全机 `Device Utilization %` 平均 **53.87%**、范围 **41–67%**。其他浏览器 GPU 进程及 WindowServer 同时活跃，因此不能将这一负载归因于 Gallery。
- 采样期间 GPU `recoveryCount` 均为 0；`pmset` 没有记录热告警或性能告警。这不提供具体温度，也不能证明所有渲染路径没有问题。
- 当前自动化接口不提供每标签页性能计数器；浏览器安全策略拒绝打开 `chrome://` 内部进程诊断页，没有绕过限制。单页 CPU、单页 GPU 与具体动画成本仍待具备授权的页面性能工具后测量。

## Memory

- API RSS 约 146–155 MiB；几个主要 worker 的 RSS 在窗口内基本稳定。短窗口没有显示服务端持续增长趋势，但不能据此排除长期泄漏。
- 系统已有约 5.53 GiB swap 使用；单次存量不能证明此刻正在换页。`memory_pressure` 报告 system-wide free percentage 40%。不将它解释为精确物理空闲 RAM 百分比。

## Recommended next steps

1. 给无任务 worker 增加有界退避和变化唤醒；共享目录选择结果，避免四个进程反复计算相同投影。不能延迟用户暂停/恢复或遗漏新增工作。
2. 用结构化版本字段/索引减少热路径 JSON 解析，并记录查询耗时。先针对 worker 验证，再检查全库 Gallery/API 聚合和轮询。
3. 采用同样的 60–90 秒采样复测：无新任务时四个 worker 应接近休眠；再测正常刮削吞吐，避免以降低实际处理速度换取 CPU 数字好看。
4. 浏览器需分别测固定封面、横滚、进入照片流、单图等状态。取得页面级工具前，不应依据全机 GPU 数值削减或宣称已优化 Gallery 动画。
