# 多图加载与预览缓存实测

日期：2026-10-26。保持内网 HTTP/1.1，不增加 HTTPS、HTTP/2、外部 CDN 或 NAS 原图缓存。

## 改动与边界

- `PreviewImage`/`PreviewSVG`复用预览调度器：可见缩略图和可见 4K 优先，其次临近视口，最后活动预热。共享 fetch 队列最多 6 个任务，后台最多 2 个；原图不进入此队列。
- Cover Flow 的缩略图保留浏览器原生 `<img>` 加载，中央封面高优先级。强制所有封面经过 fetch→Blob 的实验增加了冷启动开销，已放弃。原生前景请求也向共享调度器报告生命周期，完成后留 120ms 绘制窗口，再允许后台预热。HTTP/1.1 的实际连接调度仍由浏览器决定，不能把待发送请求数当作传输并发数。
- 其他展厅、SVG 年轮、照片流、Dashboard 照片条/目录和策展结果使用共享组件。同 URL 的 fetch 引用去重；滚动虚拟化、邻近视口加载、取消、引用计数和最后一次释放 Blob 保留。飞散动画额外持有短期引用，避免旧图卸载后动画图片失效。
- 活动仍预热前 15 张 4K（测试活动只有 14 张）。照片流先显示缩略图、4K 解码后淡入；直接复用同 URL 的预热任务，不为晚到 Blob 再替换 src。
- 只有成功的 thumb/display 响应允许浏览器保存：`private, no-cache, must-revalidate`、`Vary: Cookie`、ETag。**每次复用仍请求服务端确认**，通过登录、范围、隐藏状态、revision、文件存在检查后才可 304。文件重新生成会改变 ETag。原图、兼容原图、接口数据与错误继续 `no-store`。不是 `immutable`，也不是免鉴权的离线图库；已经显示或用户保存的内容不能由登出远程收回。
- 缓存访问时间最多每 30 秒更新一次，减少并发读图时的 SQLite 写锁争用；淘汰仍使用原有 120 秒近期访问保护。

## 测量方法

`tools/image_performance_server.py` 在独立临时 SQLite 中构造 6 个活动、84 个照片位置。图像字节是本机正式 thumb/display 缓存的只读副本，按 4K 文件大小分层抽取；元数据、事件、密码均为合成。筛掉占位图；初次样本中的一个占位替换成邻近有效样本，故有 83 对不同文件。测试不读取 NAS，不复制原图或正式凭据。私密样本、截图、原始日志位于忽略的 `data/image-performance/`。

前后使用同一批字节、固定排名及 1600×900 Chrome 视口。基线前端先构建保存，基线后端从改动前提交 `e349421` 提取；最终复测使用优化后的服务和前端。使用 HTTP/1.1：

1. **本机直连**：不人为限速，SSD/操作系统页缓存正常工作；不是冷磁盘测试。
2. **模拟内网**：Chrome CDP 设置延迟参数 10ms、上下行 100 Mbps；这是可重复的限速条件，不是实际 Wi-Fi 或路由器测量。

每个场景/条件冷、热各 3 次。冷加载清除浏览器 HTTP 缓存；热加载是在同一浏览器中重复进入同场景。记录从页面导航开始至当前可见图片全部可解码的时间；照片流还等待已挂载 4K 图淡入就绪，包含进入照片流的过渡时间。随后观察 700ms，统计媒体响应传输字节。Cover Flow 的预热在这个窗口结束时可能仍在继续，故它的传输量不能视为完整预热量。热加载是快速重复进入，并非保证所有后台预热已完成。

报告用三次中位数，同时保留最小/最大值。页面首次 JS 初始化、绘制、后台任务和本机负载均有波动；小于几十毫秒的变化不应解读为稳定收益。此次不是全库并发、多用户或弱手机压力测试。

## 结论

模拟内网中，照片流首次进入 4.820s → 3.517s（缩短 27%），重复进入 4.644s → 1.809s（缩短 61%）；器材馆重复进入 0.521s → 0.173s（缩短 67%）。照片流的重复进入媒体传输约 48.2MiB → 33.9KiB，正文由本地浏览器缓存复用，仍有鉴权/304 往返。首次照片流也避免了预热与展示重复下载同一 4K。

Cover Flow 首次进入在模拟内网基本持平（0.370s → 0.363s）；本机直连 0.346s → 0.352s。地图模拟内网首次进入 0.173s → 0.187s，慢约 14ms，没有证明冷启动收益。小页请求量少，缓存节省字节不等于同等比例缩短页面初始化/布局时间。不宣称所有页面都变快，也不把该抽样结果当作整个 NAS/SSD 的吞吐上限。
